# Python anti-slop 제안 — 미적용

추천 구성은 **짧은 Python 코딩 스킬 + 기존 Ruff/타입 검사 + 소수의 프로젝트 전용 검사**입니다. 이 문서는 설계 제안이며 스킬 등록, 기본 활성화, Python 린터 설치, CI 설정 변경은 하지 않았습니다.

## 원본에서 가져올 방향

[dmmulroy/anti-slop](https://github.com/dmmulroy/anti-slop/tree/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b)은 TypeScript/JavaScript용 Oxlint 규칙 모음입니다. 읽고 고쳐 쓰는 vendoring과 팀 기준에 맞춘 규칙을 강조합니다. Python에서는 문법을 그대로 옮기기보다 **근거 없는 타입 우회, 오류 은폐, 검증 없는 성공 처리**를 줄이는 목적을 가져오는 편이 좋겠습니다.

## 1. 코딩 스킬이 담당할 내용

새 `python-evidence-first` 스킬을 나중에 만든다면 다음 정도로 짧게 시작하는 것을 제안합니다.

- 기존 함수와 데이터 흐름을 먼저 확인하고, 요청에 필요한 최소 변경을 합니다.
- 외부 데이터·설정·모델 출력은 경계에서 검증합니다. 내부 함수마다 근거 없이 같은 방어 코드를 반복하지 않습니다.
- 실패를 `None`, 빈 리스트, `0`, 임의 기본값으로 바꾸려면 호출자가 실패와 정상 결과를 구별할 수 있는지 확인합니다.
- 예외 처리는 복구·변환·전파 목적을 드러냅니다. 재시도는 종료 조건과 실패 결과를 명시합니다.
- 테스트는 외부에서 관찰되는 동작을 검증합니다. 네트워크·파일·비용이 큰 연산의 mock은 허용하되, 바뀐 핵심 로직 전체를 mock해서 통과시키지 않습니다.
- 기존 타입 검사·테스트를 먼저 사용합니다. 작은 수정 때문에 새 프레임워크나 여러 계층의 추상화를 추가하지 않습니다.
- 완료 보고에는 실제 실행한 검증과 남은 불확실성을 적습니다. 현재 기본 스킬인 Karpathy·verification 지침과 겹치는 설명은 링크로 연결합니다.

## 2. 기존 도구로 처리할 부분

| 후보 | 도구/규칙 | 도입 방식 |
| --- | --- | --- |
| 너무 넓은 예외 처리 | Ruff `BLE001` | 경계에서 로깅·재전파하는 합당한 처리와 구분해 검토 |
| 코드 없는 `type: ignore` | Ruff `PGH003` | 무시할 타입 오류 코드를 명시 |
| 코드 없는 `noqa` | Ruff `PGH004` | 무시할 린트 규칙을 명시 |
| 이미 불필요해진 `noqa` | Ruff `RUF100` | 오래된 억제 주석을 제거 |
| 타입 계약 불일치 | 프로젝트의 기존 타입 검사기 | 전역 strict 강제보다 수정 모듈부터 확대 |

각 규칙의 정확한 예외와 한계는 공식 문서를 기준으로 정합니다: [BLE001](https://docs.astral.sh/ruff/rules/blind-except/), [PGH003](https://docs.astral.sh/ruff/rules/blanket-type-ignore/), [PGH004](https://docs.astral.sh/ruff/rules/blanket-noqa/), [RUF100](https://docs.astral.sh/ruff/rules/unused-noqa/).

Ruff는 사용자 정의 Python lint plugin을 지원하지 않습니다. 자체 규칙이 꼭 필요하다면 작은 standalone AST 검사기로 시작하고, 이미 Pylint를 쓰는 레포에서는 Pylint checker를 고려할 수 있습니다. 기본 검사와 타입 검사는 서로 보완하도록 둡니다. [Ruff FAQ](https://docs.astral.sh/ruff/faq/#can-i-write-my-own-linter-plugins-for-ruff)

## 3. 새 규칙은 처음에 2–3개만

다음은 아직 검증하지 않은 후보입니다. 넓은 정규식이나 추측에 기반해 바로 CI를 막지 않습니다.

| 후보 규칙 | 찾을 패턴 | 첫 단계와 예외 |
| --- | --- | --- |
| `PYAS001 silent-success-fallback` | 예외 뒤 상수·빈 결과를 반환해 정상 성공처럼 보이게 하는 코드 | 리뷰 경고. 실제 계약을 알 수 없으므로 모든 `return None`을 오류로 취급하지 않음 |
| `PYAS002 unbounded-retry` | 실패를 삼키고 동일 작업을 무기한 다시 시도하는 명백한 로컬 루프 | 리뷰 경고. daemon·queue consumer 등 의도적 반복은 구분. AST만으로 종료를 증명한다고 주장하지 않음 |
| `PYAS003 unexplained-suppression` | 규칙을 끄는 주석에 이유가 없거나, 파일 전체 검사를 무조건 끄는 변경 | 변경된 코드에서만 시작. PGH003/004와 중복하지 않도록 이유·범위만 추가 검사 |

규칙별로 위반 예제뿐 아니라 정당한 코드 예제도 테스트에 넣습니다. 억제 문법은 예를 들어 `# anti-slop: ignore[PYAS001] — optional metadata lookup`처럼 ID와 구체적 이유를 요구할 수 있습니다. 이 문법 역시 제안일 뿐 설치된 도구는 없습니다.

`Any`, `getattr`, `isinstance`, `dict`, dataclass, dependency injection, mock 자체를 일괄 금지하지 않는 편이 좋습니다. Python 라이브러리 경계나 연구 코드에서 정당한 사용이 많고, 이런 금지는 오히려 억제 주석과 과한 추상화를 늘릴 수 있습니다.

## 4. Python/ML 작업을 위한 선택 지침

Python이라는 이유만으로 모든 레포에 ML 규칙을 켜지는 않습니다. PyTorch·데이터 처리 작업에는 아래 내용을 선택 스킬의 리뷰 체크리스트로 둘 수 있습니다.

- 학습/평가 데이터 분리와 전처리 통계의 누수를 확인합니다.
- 평가 시 모델 모드와 gradient 사용 여부가 의도에 맞는지 확인합니다.
- NaN/Inf, 로딩 실패, 빈 batch를 조용히 버려 성공처럼 보고하지 않습니다.
- 작은 실제 데이터로 변경 경로를 실행하고, shape·dtype·device 가정을 확인합니다.
- 성능 주장은 측정한 구간·입력·장치를 함께 남깁니다.

이 항목들은 의미와 실행 맥락이 중요하므로 첫 버전의 AST 차단 규칙으로 만들지 않는 것을 추천합니다.

## 적용한다면 순서

1. 대표 Python 레포 한 곳에서 기존 검사와 실패 사례를 수집합니다.
2. 스킬만 수동 활성화해 답변·수정 품질을 확인합니다. 반복 지침과 불필요한 절차를 줄입니다.
3. 전용 규칙 후보를 경고 모드로 변경 파일에 실행하고 오탐을 분류합니다.
4. 오탐이 낮고 합의한 규칙만 CI 오류로 승격합니다. 동작을 바꾸는 자동 수정은 제외합니다.
5. 그 뒤 이 커넥터의 `AGENT_SKILLS` 카탈로그에 추가합니다. 초기에는 `defaultEnabled: false`로 제공하고 `/set_skill`로 켜게 하는 편이 좋겠습니다.

현재 구현된 확장 지점만 준비해 두었으며, 이 제안의 스킬·규칙은 `/pure` 여부와 무관하게 실행되지 않습니다.
